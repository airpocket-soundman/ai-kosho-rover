2026-09-24 に策定した計画案です。各フェーズは「完了条件」を満たしたら次へ進みます。期間は目安で、実測結果や部品の入手状況に応じて[進捗](../progress/)で更新します。

## 全体の流れ

```text
Phase 0  準備            部品発注、開発環境、公開サイト
Phase 1  走行台車        LEGO + Geekservo + メカナム、手動操縦、安全停止
Phase 2  自己位置        外部カメラ + AprilTag、ウェイポイント走行
Phase 3  台とリフト      台の製作、ドッキング、持ち上げ搬送
Phase 4  下半身検出      画像収集 → ラベリング → 学習 → UNO Q で実行   (Phase 1〜3 と並行)
Phase 5  玄関イベント    人物検出・識別、扉の開閉、行動の時系列化
Phase 6  判断モデル      LAYA の実行検証、状態テキスト設計、ルールベースとの比較
Phase 7  統合            外出・帰宅シナリオの通し試験、能動観測、評価
Phase 8  まとめ          記録の整理、公開
```

## フェーズ詳細

### Phase 0: 準備(2026-09-24 〜 10 月上旬)

| 作業 | 内容 |
| --- | --- |
| 部品発注 | 下記の部品表に沿って発注。納期の長いメカナムホイールと UNO Q を先に |
| 開発環境 | Arduino App Lab、UNO Q の Debian 初期設定、PC 側の Python / PyTorch / CUDA 環境 |
| 公開サイト | GitHub Pages(このサイト)を公開し、進捗ログの書き方を決める |
| 家庭環境の採寸 | 廊下・玄関・収納スペースの寸法、床材、カメラ設置候補の高さを記録 |

完了条件: 主要部品が手元にあり、UNO Q で Python と Sketch が動き、このサイトが公開されている。

### Phase 1: 走行台車(10 月)

| 作業 | 内容 |
| --- | --- |
| フレーム | LEGO Technic で車台を組み、Geekservo ×4 とメカナムを取り付ける |
| 電装 | モーターシールドの接続、電源の分離、電圧監視 |
| MCU ファームウェア | メカナム運動学(vx, vy, ω → 4 輪 PWM)、ウォッチドッグ、速度上限 |
| 安全停止 | ToF ×4 とバンパーによる停止を MCU 単独で動作させる |
| 手動操縦 | PC のゲームパッドまたはブラウザから Wi-Fi 経由で操縦 |
| 走行試験 | フローリングで前後・左右・斜め・その場回転。積載 600 g での走行 |

完了条件: 積載 600 g で 0.1 m/s の全方向移動ができ、障害物 12 cm で自動停止し、指令が途切れると 300 ms 以内に止まる。

### Phase 2: 自己位置(10 月下旬 〜 11 月中旬)

| 作業 | 内容 |
| --- | --- |
| ESP32-CAM | MJPEG 配信のファームウェア、固定用マウント、fps と遅延の測定 |
| 外部カメラ設置 | 廊下を俯瞰する位置に設置。床基準タグでホモグラフィ校正 |
| 位置推定 | ローバー上面の AprilTag から (x, y, θ) を 10 Hz で出力 |
| ウェイポイント走行 | P 制御で目標点へ移動。到達精度と再現性の測定 |
| 死角対策 | タグが見えないときの停止、IMU での補間(任意) |

完了条件: 5 点のウェイポイントを ±5 cm、±5° で連続到達し、30 分の連続運転で位置推定が破綻しない。

### Phase 3: 台とリフト(11 月)

| 作業 | 内容 |
| --- | --- |
| 台の製作 | LEGO で脚付きの台を 3 台(父・母・子)+ 傘用 1 台。下面に芯出し用の受け皿 |
| リフト | サーボ + 平行リンクでストローク 10〜15 mm。600 g の保持試験 |
| ドッキング | 前方カメラで台の脚のタグを検出し、横移動で芯合わせ、潜り込み、リフト |
| 搬送 | 収納スペース → 玄関 → 収納スペースの往復。荷物の落下がないこと |

完了条件: 台のドッキング成功率 9/10 以上、600 g 積載で廊下往復 10 回連続成功。

### Phase 4: 下半身検出モデル(10 月 〜 12 月、並行)

詳細は[データセット計画](../dataset/)を参照。

| 作業 | 内容 |
| --- | --- |
| 収集 | ローバー前方カメラ(または同じ高さに置いた ESP32-CAM)で玄関・廊下の画像を収集 |
| ラベリング | クラス定義に沿ってバウンディングボックスを付与(担当: 本人) |
| 学習 | PC の GPU で YOLO 最小モデルを学習。データ拡張と検証 |
| 配備 | ONNX に変換して UNO Q で実行。fps とメモリの測定 |
| 評価 | 靴の着脱、しゃがみ、荷物の検出精度を実環境で確認 |

完了条件: 検証セットで mAP50 が 0.7 以上、UNO Q で 5 fps 以上。

### Phase 5: 玄関イベント(12 月)

| 作業 | 内容 |
| --- | --- |
| 人物検出 | 外部カメラで人物検出(既存モデル)。足元位置を床座標に変換 |
| 人物識別 | 家族の全身画像で分類モデルを学習。日ごとの服装変化への対応を検証 |
| 扉の開閉 | リードスイッチ + 画像変化。開閉のログ |
| 状態系列 | 「廊下 → 玄関接近 → 靴付近で停止 → しゃがむ → 扉付近で立つ」などの時系列を作り、状態テキストに変換 |

完了条件: 1 週間のログで外出・帰宅のイベントを 9 割以上正しく時系列化できる。

### Phase 6: 判断モデル(12 月 〜 2027 年 1 月)

| 作業 | 内容 |
| --- | --- |
| LAYA 実行検証 | UNO Q(4 GB)で ONNX int8 の LAYA を動かし、メモリと 1 問あたりの遅延を測る |
| 状態テキスト設計 | Phase 5 の時系列を 200 トークン以下に圧縮する書式を決める |
| 質問設計 | next_action(choice)、going_out(noul)、urgency(score)の 3 問を基本にする |
| ルールベース比較 | 同じ入力で動くルールベース版を作り、一致率と誤介入率を比較 |
| 代替経路 | UNO Q で成立しない場合は自宅 PC の GPU で実行し LAN 経由で返す |

判断の分かれ目: UNO Q 上で 2 秒以内に 3 問を答えられなければ PC 実行に切り替える。

完了条件: 記録済みの状態系列 50 件に対し、期待する行動との一致率が 8 割以上。

### Phase 7: 統合(2027 年 1 月)

| 作業 | 内容 |
| --- | --- |
| 外出シナリオ | 人物識別 → 外出予測 → 台の搬送 → 受け渡し → 扉の閉鎖確認 → 台の収納 → 帰還 |
| 帰宅シナリオ | 扉の開放 → 人物識別 → 空の台で迎え → 受け取り → 収納 → 帰還 |
| 能動観測 | 判断に迷ったときの OBSERVE 行動と、その後の再判断 |
| 評価 | 適切な介入、誤介入、見逃し、所要時間、安全停止の回数を 1 週間記録 |

完了条件: 家族の外出・帰宅 20 回のうち、適切な介入が 7 割以上、危険な接触が 0 回。

### Phase 8: まとめ(2027 年 2 月)

配線図、部品表、再現手順、評価結果、うまくいかなかったことをサイトに整理して公開する。

## リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| Geekservo のトルク不足 | 積載で走れない | LEGO ギアで減速。総重量を 1.5 kg 以下に抑える |
| ESP32-CAM の遅延・コマ落ち | 位置制御が不安定 | 速度を 0.1 m/s に抑え、専用 SSID。必要なら ESP32-S3 |
| LAYA が UNO Q で重い | 判断周期が長い | int8 化、状態圧縮。不成立なら PC 実行に切替 |
| 画像データの不足 | 検出精度が出ない | 収集を Phase 1 から並行して始め、家族の協力で服装・時間帯を変える |
| 人物識別の不安定さ | 台を取り違える | 台の受け渡し前に人物の再確認を入れ、確信度が低ければ OBSERVE を選ぶ |
| 家庭内での安全 | 足に当たる、荷物を落とす | MCU 単独の停止、速度上限、人の 30 cm 以内で減速、物理スイッチ |

## 進め方のルール

- 各フェーズの完了条件を満たしたら、[進捗](../progress/)にチェックを入れ、進捗ログ(ホームの一覧)に記事を書く。
- 実測値が出たら[詳細検討](../design/)の「計算値」を実測値に置き換える。
- 家庭内の映像・人物データは公開しない。公開するのは匿名化した例と統計だけにする。
