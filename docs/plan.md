2026-09-24 に策定した計画案です(同日に自己位置推定とサーバー構成を改訂)。各フェーズは「完了条件」を満たしたら次へ進みます。期間は目安で、実測結果や部品の入手状況に応じて[進捗](../progress/)で更新します。

## 全体の流れ

```text
Phase 0  準備            部品発注、開発環境、公開サイト、採寸と地図
Phase 1  走行台車        LEGO + Geekservo + メカナム、手動操縦、安全停止、操縦ログの記録
Phase 2  自己位置        LD06 + 事前地図 + フローセンサー + IMU、ウェイポイント走行
Phase 3  台とリフト      台の製作、ドッキング、持ち上げ搬送、充電ステーションへの自動帰還
Phase 4  下半身検出      画像収集 → ラベリング → 学習 → UNO Q で実行   (Phase 1〜3 と並行)
Phase 5  玄関イベント    人物検出・識別、扉の開閉、行動の時系列化、常時監視の連続運転
Phase 6  判断と学習制御  LAYA サーバー、通信とフォールバック、ドッキングの模倣学習
Phase 7  統合            外出・帰宅シナリオの通し試験、能動観測、電子音の表現、評価
Phase 8  まとめ          記録の整理、公開
```

## フェーズ詳細

### Phase 0: 準備(2026-09-24 〜 10 月上旬)

| 作業 | 内容 |
| --- | --- |
| 部品発注 | 下記の部品表に沿って発注。納期の長いメカナムホイール、UNO Q、PAA5100JE を先に |
| 開発環境 | Arduino App Lab、UNO Q の Debian 初期設定、PC 側の Python / PyTorch / CUDA 環境、LAYA の PC 上での動作確認 |
| 公開サイト | GitHub Pages(このサイト)を公開し、進捗ログの書き方を決める |
| 採寸と地図 | 廊下・玄関・収納スペースの寸法、床材、扉枠や下駄箱の位置を測り、占有格子地図の下書きを作る。外部カメラの設置位置も決める |

完了条件: 主要部品が手元にあり、UNO Q で Python と Sketch が動き、PC で LAYA が応答し、このサイトが公開されている。

### Phase 1: 走行台車(10 月)

| 作業 | 内容 |
| --- | --- |
| フレーム | LEGO Technic で車台を組み、Geekservo ×4 とメカナムを取り付ける。LD06 を中段に置き、リフト板を支える柱を斜め 45° 方向に 4 本立てる。車高を確認 |
| 待機位置 | 収納スペースに充電ステーションの場所を決め、手動で USB を挿す形で待機位置として使い始める。UNO Q のアイドル消費を実測する |
| 音 | 音声出力回路(DFPlayer Mini + スピーカー + BUSY 信号 + 圧電ブザー)を組み、MCU から曲番号と音量で再生。小姓語の WAV を microSD に入れる |
| 電装 | モーターシールドの接続、電源の分離、電圧監視 |
| MCU ファームウェア | メカナム運動学(vx, vy, ω → 4 輪 PWM)、ウォッチドッグ、速度上限 |
| 安全停止 | ToF ×4 とバンパーによる停止を MCU 単独で動作させる |
| 手動操縦 | PC のゲームパッドまたはブラウザから Wi-Fi 経由で操縦 |
| ログ記録 | 観測(センサー、カメラ)と指令のペアを自動記録する仕組みを入れる。Phase 6 の模倣学習のデータになる |
| 走行試験 | フローリングで前後・左右・斜め・その場回転。積載 600 g での走行 |

完了条件: 積載 600 g で 0.1 m/s の全方向移動ができ、障害物 12 cm で自動停止し、指令が途切れると 300 ms 以内に止まる。

### Phase 2: 自己位置(10 月下旬 〜 11 月中旬)

| 作業 | 内容 |
| --- | --- |
| LD06 接続 | MCU の UART で受信し、1 回転分を Bridge で Linux 側へ転送。転送量と取りこぼしを確認。MOSFET で電源を制御 |
| 柱マスク | ホーム位置の静止スキャンから柱の角度を求め、尤度計算から除外する |
| 地図 | 採寸から 2〜5 cm 格子の占有格子地図を作る。走査面(床上 50〜60 mm)で見える形になるよう、既知位置の実測スキャンと重ねて修正 |
| フローセンサー + IMU | SPI / I2C で読み、50 Hz で増分を出す。床材ごとの係数を測る |
| 位置合わせ | パーティクルフィルタ(尤度場)を numpy で実装。粒子数と処理時間を測る |
| ウェイポイント走行 | P 制御で目標点へ移動。到達精度と再現性の測定 |
| 見失い対策 | 位置合わせの失敗検出、フロー + IMU での継続、5 秒で停止、再推定 |

完了条件: 5 点のウェイポイントを ±5 cm、±5° で連続到達し、30 分の連続運転で位置推定が破綻しない。

### Phase 3: 台とリフト(11 月)

| 作業 | 内容 |
| --- | --- |
| 台の製作 | LEGO で脚付きの台を 3 台(父=赤、母=青、子=黄)+ 傘用 1 台。下の空間 120 mm、下面に芯出し用の受け皿 |
| リフト | サーボ + 平行リンクでストローク 10〜15 mm。接触スイッチ。600 g の保持試験 |
| ドッキング | 前方カメラで台の脚を検出し、横移動で芯合わせ、潜り込み、ToF で停止、リフト |
| 搬送 | 収納スペース → 玄関 → 収納スペースの往復。荷物の落下がないこと |
| 充電ステーション | 送電パッド台座と側壁・奥壁を作り、ToF と受電電流で自己整列して充電を確認。パススルー充電の動作確認 |
| ログ記録 | ドッキングの観測と指令を記録(模倣学習用) |

完了条件: 台のドッキング成功率 9/10 以上、600 g 積載で廊下往復 10 回連続成功、充電ステーションへの自動帰還と受電開始 9/10 以上。

### Phase 4: 下半身検出モデル(10 月 〜 12 月、並行)

詳細は[データセット計画](../dataset/)を参照。

| 作業 | 内容 |
| --- | --- |
| 収集 | ローバー前方カメラ(または同じ高さに置いた ESP32-CAM)で玄関・廊下の画像を収集 |
| ラベリング | クラス定義に沿ってバウンディングボックスを付与(担当: 本人) |
| 学習 | PC の GPU で YOLO 最小モデルを学習。データ拡張と検証 |
| 配備 | ONNX に変換して UNO Q で実行。fps とメモリの測定 |
| 評価 | 靴の着脱、しゃがみ、荷物、台の脚の検出精度を実環境で確認 |

完了条件: 検証セットで mAP50 が 0.7 以上、UNO Q で 5 fps 以上。

### Phase 5: 玄関イベント(12 月)

| 作業 | 内容 |
| --- | --- |
| 人物検出 | 外部カメラで人物検出(既存モデル)。足元位置の追跡 |
| 人物識別 | 家族の全身画像で分類モデルを学習。日ごとの服装変化への対応を検証 |
| 扉の開閉 | リードスイッチ + 画像変化。開閉のログ |
| 状態系列 | 「廊下 → 玄関接近 → 靴付近で停止 → しゃがむ → 扉付近で立つ」などの時系列を作り、状態テキストに変換 |
| 生活パターン | 人ごとの外出・帰宅時刻をログに残し、平日 / 休日 × 30 分刻みで集計。初期値(平日朝は娘と父が外出、夕方に帰宅)は手入力 |
| 常時監視 | MQTT ブローカーを PC に立て、扉・人物・ローバー状態を流す。外部カメラの人物検出と扉の監視は PC で行い、ローバーは「出番」通知で起きる。ステーション上で 1 週間連続運転し、充電の収支・Wi-Fi の切断回数を記録 |

完了条件: 1 週間のログで外出・帰宅のイベントを 9 割以上正しく時系列化できる。

### Phase 6: 判断と学習制御(12 月 〜 2027 年 1 月)

| 作業 | 内容 |
| --- | --- |
| LAYA サーバー | PC 上で LAYA を HTTP サービスにし、状態テキスト JSON を受けて 3 問を返す。遅延を測る |
| 状態テキスト設計 | Phase 5 の時系列と自己位置・台の状態、生活パターンの傾向(`routine:` 行)を含む書式を決める |
| 質問設計 | next_action(choice)、going_out(noul)、urgency(score)の 3 問を基本にする |
| 通信とフォールバック | 応答なし 500 ms で直前の行動を維持、5 秒で WAIT。サーバー停止試験 |
| ルールベース比較 | 同じ入力で動くルールベース版を作り、一致率と誤介入率を比較。生活パターンで兆候の必要数を変える規則を含める |
| ドッキングの模倣学習 | Phase 1・3 のログで小さな MLP / GRU を学習し、UNO Q で実行。古典制御と成功率を比較 |
| 機体側の意図予測(任意) | 記録済み系列で「30 秒以内に外出」の確率を出す小型モデル |

完了条件: 記録済みの状態系列 50 件に対し、期待する行動との一致率が 8 割以上。学習ポリシーのドッキング成功率が古典制御と同等以上。

### Phase 7: 統合(2027 年 1 月)

| 作業 | 内容 |
| --- | --- |
| 外出シナリオ | 人物識別 → 外出予測 → 台の搬送 → 受け渡し → 扉の閉鎖確認 → 台の収納 → 帰還 |
| 帰宅シナリオ | 扉の開放 → 人物識別 → 空の台で迎え → 受け取り → 収納 → 帰還 |
| 能動観測 | 判断に迷ったときの OBSERVE 行動と、その後の再判断 |
| 電子音 | 8 種類の音を PC で合成し、行動状態機械の遷移に結び付ける。時刻による音量切り替え。家族の反応で調整 |
| 評価 | 適切な介入、誤介入、見逃し、所要時間、安全停止の回数を 1 週間記録 |

完了条件: 家族の外出・帰宅 20 回のうち、適切な介入が 7 割以上、危険な接触が 0 回。

## リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| Geekservo のトルク不足 | 積載で走れない | LEGO ギアで減速。総重量を 1.5 kg 以下に抑える |
| 廊下で自己位置が曖昧 | ウェイポイントを外す | 地図に扉枠や下駄箱を入れる。フロー + IMU で補う。見失ったら停止 |
| 柱の死角と低い走査面 | 位置推定の精度低下 | 柱を斜め方向に置きマスク処理。走査面の高さで地図を作る |
| LD06 の寿命(10,000 時間) | 常時稼働で 1 年強 | 待機中は電源を切る |
| 無線給電の出力不足(5 W) | 充電が進まない | 待機中の監視は PC、ローバーはアイドル(2〜2.5 W 見込み、要実測)。不足なら送受電セットを 2 組に |
| 無線給電の位置ずれ | 受電できない | ToF で壁との距離を合わせ、受電電流が最大になる位置を探す |
| 常時監視の Wi-Fi 断 | 監視の停止 | 監視は PC 側。ローバーは自動再接続 |
| フローセンサーの入手遅れ | Phase 2 の遅延 | Amazon の PMW3901 で先に実験し、到着後に載せ替える。同じドライバで動く |
| ESP32-CAM の遅延・コマ落ち | 認識の遅れ | 位置制御はカメラに依存しない設計。専用 SSID。必要なら ESP32-S3 |
| サーバー停止・通信断 | 判断が止まる | 500 ms / 5 秒のフォールバック。安全停止と自己位置は機体側で完結 |
| 画像データの不足 | 検出精度が出ない | 収集を Phase 1 から並行して始め、家族の協力で服装・時間帯を変える |
| 人物識別の不安定さ | 台を取り違える | 受け渡し前に人物を再確認し、確信度が低ければ OBSERVE を選ぶ。台は色でも確認 |
| 模倣学習の失敗 | ドッキングが不安定 | 古典制御をフォールバックに残し、成功率で切り替える |
| 家庭内での安全 | 足に当たる、荷物を落とす | MCU 単独の停止、速度上限、人の 30 cm 以内で減速、物理スイッチ |

## 進め方のルール

- 各フェーズの完了条件を満たしたら、[進捗](../progress/)にチェックを入れ、進捗ログ(ホームの一覧)に記事を書く。
- 実測値が出たら[詳細検討](../design/)の「計算値」を実測値に置き換える。
- 家庭内の映像・人物データは公開しない。公開するのは匿名化した例と統計だけにする。
