企画書の構想を、決定済みの制約に沿って具体化した結果です。
数値は公開されている仕様や計算値で、実測で更新します。未確認の項目は「要確認」と明記しています。

決定済みの制約(2026-09-24 時点):

- 駆動は Geekservo の DC モーター、フレームは LEGO Technic。
- 荷物を載せた「台」の下に潜り込み、リフトで持ち上げて運ぶ。
- 走行領域を俯瞰できる場所にカメラを置けないため、自己位置推定はローバー単独で行う。手持ちの LDROBOT LD06 を使う。
- AprilTag などの標識は家の中に貼らない。
- 外部カメラ(ESP32-CAM)は玄関に人が来ることや扉の開閉の検出に使う。
- LAYA は自宅 PC のサーバーで動かし、機体側には学習ベースの身体制御を持たせる。
- LD06 は最上部には置けず中段に搭載する。上のリフト板を支える 4 本の柱で死角ができる。
- 待機位置は充電ステーションとし、待機中も常時 Wi-Fi で玄関を監視する。
- 言葉ではなく R2-D2 のような電子音で「持ってきたよ」「おかえり」「いってらっしゃい」を表現する。
- ローバー視点(下半身)の画像を収集し、自分でラベリングして検出モデルを作る。

## 1. 全体構成(三層)

```text
┌──────────────── 自宅 PC(LAN 内サーバー、NVIDIA GPU) ────────────────┐
│  LAYA(型付き Decision Model)                                          │
│   入力: 状態テキスト   出力: next_action / going_out / urgency          │
│  判断周期 0.2〜0.5 秒。画像は送らず、テキストの状態だけを送る            │
└───────────────────────────────┬────────────────────────────────────┘
                                │ Wi-Fi / HTTP(JSON)  応答なし 500 ms → 直前の行動を維持
                                │                     応答なし 5 s   → WAIT または RETURN_HOME
┌───────────────────────────────▼────────────────────────────────────┐
│ Arduino UNO Q  Linux 側(Cortex-A53 ×4、Debian、Python)                │
│  ・LD06 の点群 + 事前地図 → パーティクルフィルタで自己位置 (x, y, θ)      │
│  ・床面フローセンサー + IMU で観測間の補間                                 │
│  ・前方カメラ: 下半身検出、台の脚検出、台の色識別                          │
│  ・外部カメラ: 人物検出・識別、玄関到着、扉の開閉                          │
│  ・状態系列の構築 → サーバーへ送信、行動の受信                             │
│  ・身体制御: ウェイポイント追従(古典)+ ドッキング・接近(学習ポリシー)     │
└───────────────────────────────┬────────────────────────────────────┘
                                │ Arduino Bridge(RPC)  目標速度 vx, vy, ω / リフト指令
┌───────────────────────────────▼────────────────────────────────────┐
│ Arduino UNO Q  MCU 側(STM32U585)                                      │
│  ・メカナム運動学 → 4 輪 PWM                                            │
│  ・ToF / バンパー → 非常停止(Linux 側・サーバーと独立)                    │
│  ・指令が 300 ms 途切れたら停止するウォッチドッグ、速度上限               │
│  ・LD06 の UART 受信、フローセンサーの SPI 読み出し、IMU、電池電圧         │
└───────────────────────────────┬────────────────────────────────────┘
                                │
      モータードライバ → Geekservo DC ×4 → メカナムホイール ×4
      サーボ → リフト
```

三層の分担は次の通りです。

| 層 | 場所 | 周期 | 担当 |
| --- | --- | --- | --- |
| 遅い判断 | 自宅 PC の LAYA | 0.2〜0.5 秒 | 何をするか(行動の選択、外出・帰宅の判定、緊急度) |
| 速い身体制御 | UNO Q の Linux 側 | 10〜20 Hz | どう動くか(自己位置、経路、ドッキング、人への接近) |
| 最後の安全 | UNO Q の MCU 側 | 100 Hz 以上 | 止まるべきか(近接停止、接触停止、ウォッチドッグ) |

サーバーが止まっても機体は安全に停止でき、機体の Linux 側が止まっても MCU は停止できます。

## 2. 機体(フレーム・駆動・車輪)

### 2.1 駆動モーター: Geekservo DC モーター(赤、2 線)

| 項目 | 値 |
| --- | --- |
| 動作電圧 | 3.3〜6 V(定格 4.8 V) |
| 最高回転数 | 70 rpm |
| 最大トルク | 500 g·cm |
| 定格電流 / 拘束電流 | 200 mA / 700 mA |
| 出力軸 | LEGO Technic 十字軸 |
| 備考 | ギア保護用クラッチ内蔵。極性反転で逆転。エンコーダーなし |

兄弟品の Geekservo 2 kg モーター(90 rpm、500 g·cm、両軸)はトルクが同じで速度が高いだけなので、まずは小型の 9 g 赤モーターを採用します。

### 2.2 車輪: 60 mm LEGO 互換メカナムホイール

Nexus Robot 14144 系の 60 mm LEGO 互換メカナム(左右 2 個ずつ、Technic ハブ付き)を第一候補にします。Geekservo の十字軸に直結できます。予備案として Technic 軸対応の 3D プリント 70 mm メカナム(Thingiverse / Cults3D に公開データあり)を用意します。

### 2.3 計算上の性能(要実測)

| 項目 | 計算値 | 前提 |
| --- | --- | --- |
| 最高速度 | 約 0.22 m/s | 70 rpm × π × 60 mm |
| 実用速度 | 0.10〜0.15 m/s | 負荷時の回転低下を見込む |
| 1 輪あたり推進力 | 約 170 gf | 500 g·cm ÷ 3 cm |
| 横移動時の合計推進力 | 約 330 gf | メカナム横移動の効率を 50 % と仮定 |
| 総重量の上限目安 | 約 1.5〜2.0 kg | フローリングの転がり抵抗を重量の 10 % 以下と仮定 |

フローリングでは成立する見込みですが、カーペットや段差では不足する可能性があります。不足した場合は LEGO ギア(12T:20T など)で減速してトルクを 1.5 倍程度に上げます。速度は約 45 rpm に落ちますが、廊下 5 m を 40 秒程度で移動でき、用途上は問題ありません。

### 2.4 フレームと搭載配置

- LEGO Technic のビームとフレームで、平面に近い低い車台を作る。
- 目標寸法: 幅 180 mm × 長さ 200 mm 以内。車高はリフト板の上面まで 100 mm 以下(車台 + LD06 層 34 mm + リフト板)。
- 4 輪はモーターを直付けし、軸受けを Technic フレームで両持ちにして車輪のガタを抑える。
- **LD06 は車台の中段中央**に置く。その上にリフト板が載るため、リフト板を支える柱が LD06 の走査面を横切る。柱の扱いは 3.4.1 節。
- LD06 の走査面には柱以外の部品を置かない。リフト板の下面と LD06 上端の間は 10 mm 以上あけ、垂れ下がる配線を走査面に入れない。
- **床面フローセンサーは車台の底面中央**に下向きに付け、床からセンサー面まで 20〜30 mm にする(PAA5100JE の動作範囲 15〜35 mm)。
- IMU は車台の中央、振動の少ない位置に固定する。
- UNO Q、電池、モータードライバはフレーム中央に載せて重心を低く保つ。
- 前面下部に ESP32-CAM を床上 8〜10 cm の高さで前向きに固定する。
- 上面の色は台の色と混同しない色にする(台の識別に色を使うため)。

## 3. 自己位置推定(ローバー単独)

### 3.1 方針

エンコーダーがなく、メカナムは滑りが大きく、標識も貼らない条件なので、**LD06 と事前地図による位置合わせを主系**にし、**床面フローセンサー + IMU を補系**にします。学習は使いません。古典手法で十分な精度が出て、失敗の原因を追いやすいためです。

### 3.2 LD06 の仕様(データシートより)

| 項目 | 値 |
| --- | --- |
| 測距方式 | DTOF、905 nm、クラス 1 |
| 測距範囲 | 0.02〜12 m(反射率 70 %) |
| 精度 | ±45 mm(0.3 m 以下)、±30 mm(0.3〜12 m) |
| サンプリング | 4,500 点/秒 |
| 回転数 | 10 Hz 標準(PWM で 5〜13 Hz) |
| 角度分解能 | 1° |
| 寸法 / 重量 | 38.6 × 38.6 × 33.5 mm / 42 g |
| 電源 | 5 V(4.5〜5.5 V)、起動 300 mA、動作 180 mA |
| 通信 | UART 230400 8N1、片方向(Tx のみ)、ZH1.5-4P コネクタ |
| PWM | 未接続なら内蔵制御で 10 Hz |

### 3.3 地図

- 廊下・玄関・収納スペースを採寸し、2〜5 cm 格子の占有格子地図を手で作る。壁、下駄箱、扉枠、収納棚を書き込む。
- SLAM は使わない。企画書の「事前地図 + Localization」をそのまま採る。
- 地図は静止物のみ。人や台は地図に入れず、観測から除外する(15 cm 未満の点は台の脚とみなして捨てる)。

### 3.4 位置合わせ

- パーティクルフィルタ(尤度場モデル)。500 粒子 × 360 点の尤度計算は numpy で 10 Hz が見込める(要実測)。
- 予測ステップにはフローセンサー(並進)と IMU(回転)の増分を使う。
- 期待精度は ±3〜5 cm、±2°。廊下の直線区間では進行方向が曖昧になりうるが、家庭の廊下は短く両端の壁や扉枠が 4 m 以内に見えるので実用上は問題ないと見ている。
- 初期位置はホームポジションで既知とし、電源投入時はそこから始める。位置を見失ったら停止し、全域に粒子を撒いて再推定する。

### 3.4.1 柱による死角の扱い

LD06 は中段搭載で、リフト板を支える 4 本の柱が走査面を横切ります。これを前提に設計します。

| 項目 | 方針 |
| --- | --- |
| 柱の本数と位置 | 4 本。前後左右の正面を避け、**斜め 45°、135°、225°、315° 方向**に置く。前方(ドッキング、ToF)と左右(壁)の視野を確保する |
| 柱の太さと距離 | 1 スタッド幅(約 8 mm)の Technic ビーム。LD06 中心から 40 mm 以上離す |
| 死角の大きさ | 中心から 40 mm で約 12°、60 mm で約 8°。4 本で合計 30〜50°、360° の 1 割前後。300 点以上が残る |
| 点群の処理 | 起動時にホーム位置で静止スキャンを取り、距離 10 cm 未満で常に返る角度を「柱マスク」として保存。以後その角度の点は尤度計算から除外する |
| 位置推定への影響 | 尤度場モデルは点ごとに独立に評価するので、欠けた角度があっても成立する。マスクは対称に近いので推定の偏りは小さい |
| 台の脚との区別 | 柱マスクの角度は固定、台の脚は潜り込みで角度が変わる。マスク外の 15 cm 未満の点を脚とみなす |
| 走査面の高さ | 床上 50〜60 mm 程度。靴、下駄箱の下部、幅木、台の脚が見える。机や棚の天板は見えない |

走査面が低いため、地図は「その高さで見える形」で作る必要があります。採寸の下書きに加えて、既知の位置で取った実測スキャンを重ねて修正します。床に置かれた靴やかばんは地図に入れず、動的障害物として扱います。

### 3.5 補系: 床面フローセンサー + IMU

| 手段 | 役割 | 特徴 |
| --- | --- | --- |
| PAA5100JE(床面オプティカルフロー) | 並進の増分 | マウスと同じ原理で床を見る。メカナムの滑りの影響を受けない。白色 LED 内蔵で暗い廊下でも動く |
| IMU(BNO055 等)のヨー角 | 回転の増分 | 数十秒ならドリフトは小さい |

フローセンサーの出力はカウント値で、床材ごとに mm/カウントの係数が変わります。LD06 の位置推定と突き合わせて係数を自動校正します。

### 3.6 フローセンサーの選定

| 候補 | 動作距離 | 照明 | 入手性(2026-09-24 時点) | 評価 |
| --- | --- | --- | --- | --- |
| PAA5100JE(Pimoroni PIM573) | 15〜35 mm | 白色 LED ×2 内蔵 | 秋月・スイッチサイエンスに取り扱いなし。Pimoroni 直販、RobotShop、The Pi Hut などから購入 | **採用**。車台底面の高さに合い、暗所でも動く。242 fps、最大 1.14 m/s |
| PMW3901(汎用モジュール) | 80 mm 以上 | なし(外光頼み) | Amazon.co.jp で即納、スイッチサイエンスの Pimoroni 版は売り切れ。購入先は [AliExpress](https://ja.aliexpress.com/item/1005009903523306.html) に決定 | 国内即納の代替。車台最上部に置き、LEGO フレームに縦の穴を開けて床を見る。暗所用に白色 LED を横に追加する必要がある |
| USB 光学マウス(市販品) | 2〜3 mm(床に接触) | 内蔵 | どこでも買える | 実験用。ばね付きのそりに載せて床を滑らせ、Linux の入力デバイスとして読む。回転は測れない |

PAA5100JE は SPI 接続で、MCU 側から Arduino 用ドライバ(PAA5100JE と PMW3901 の両対応)で読みます。PMW3901 に切り替えても同じドライバとコードで動くので、先に Amazon で PMW3901 を買って実験を始め、PAA5100JE の到着後に載せ替える進め方もできます。

### 3.7 接続

- LD06 は MCU 側の UART で受け(約 18 kB/s)、1 回転分(360 点)にまとめて Bridge で Linux 側へ渡す(約 7 kB/s)。UNO Q の USB-C は給電で塞がるため、USB-UART 変換は使わない。
- フローセンサーは MCU 側の SPI、IMU は I2C。MCU で増分をまとめて 50 Hz で Linux 側へ渡す。

### 3.8 将来の Physical AI 要素

運用中に「前方カメラ画像と LD06 の位置」のペアが自動で溜まります。これを教師データにして、画像だけから粗い位置を出す小さなモデルを機体側で学習できます。LD06 が教師、カメラが生徒という形です。

## 4. 搬送: 台の下に潜って持ち上げる

倉庫ロボット(Kiva 方式)と同じ考え方で、荷物を載せた「台」の下にローバーが潜り込み、リフトで台ごと持ち上げて運びます。

### 4.1 台の設計

```text
       ┌───────────────────────┐  ← 天板: 財布・鍵・時計を置く
       │  父=赤 母=青 子=黄     │     LEGO の色で台を識別
       └┬─────────────────┬───┘
        │                   │      ← 脚: 4 本
        │   ローバーが潜る   │
        │   空間 120 mm 以上  │      (LD06 を含む車高 100 mm + 余裕)
   ─────┴───────────────────┴─────  床
```

- 台は LEGO で製作。脚の内寸はローバー幅 + 左右 20 mm 以上の余裕を取る。
- 台の下面中央に「受け皿」(凹み)を作り、ローバーのリフト先端の凸部が入ることで持ち上げ時に自動で芯出しされるようにする。
- 台の質量目標: LEGO 部分 200〜300 g、荷物 300 g 程度、合計 500〜600 g。
- どの台かは **LEGO の色**と**収納スロットの位置**の両方で確認する。標識は貼らない。

### 4.2 リフト機構

- 駆動: Geekservo 2 kg 270° サーボ(LEGO 互換、位置制御)×1。9 g 270° サーボを使う場合はてこ比で負荷を下げる。
- 方式: サーボでクランクを回し、平行リンクで天板を 10〜15 mm 上下させる。ストロークは台の脚が床から離れるだけで十分。
- リフト板に接触スイッチを付け、台に当たったこと、持ち上がったことを検出する。
- 持ち上げ時の目標: 台 + 荷物 600 g をリフトし、走行中に傾かないこと。サーボの保持トルクは要実測。

### 4.3 ドッキング手順

1. 自己位置推定で台の正面 30 cm のウェイポイントへ移動する(古典制御)。
2. 前方カメラで台の脚を検出し(`stand_leg` クラス)、脚 2 本の画素上の間隔と位置から距離と左右ずれを出す。脚の色で台を確認する。
3. 横移動で中心を合わせ、低速で前進して潜り込む。この区間は学習ポリシー(第 7 節)に置き換えていく。
4. 前方 ToF で奥側の脚との距離を見て停止する。LD06 の 15 cm 未満の点でも脚 4 本の配置を確認できる。
5. リフトを上げ、接触スイッチで持ち上がりを確認する。
6. 目的地へ搬送し、逆手順で降ろす。

## 5. 電装

### 5.1 コンピュータ: Arduino UNO Q

| 項目 | 値 |
| --- | --- |
| MPU | Qualcomm Dragonwing QRB2210、Cortex-A53 ×4 @ 2.0 GHz、Adreno GPU |
| MCU | STM32U585、Cortex-M33 @ 160 MHz、2 MB Flash、786 kB SRAM |
| RAM / ストレージ | 2 GB または 4 GB LPDDR4 / 16 GB eMMC |
| 無線 | Wi-Fi 5(2.4 / 5 GHz)、Bluetooth 5.1 |
| OS / 開発 | Debian Linux + Arduino App Lab(Sketch + Python + Bricks) |
| 拡張 | UNO ヘッダー、Qwiic(I2C)、MIPI-CSI カメラコネクタ |

LAYA をサーバー側に置くため、**2 GB 版で足ります**。4 GB 版なら将来、機体側で LAYA を動かす実験の余地が残ります。USB-C ポートは 1 つで給電に使うため、USB カメラや USB-UART は使いません。

### 5.2 モータードライバ

- 第一候補: Adafruit Motor Shield V2 互換品(TB6612 ×2、DC モーター 4 個、I2C 制御、サーボ用ピン 2 本)。UNO ヘッダーに重ねるだけで配線が少なく、MCU 側の I2C だけで制御できる。
- 予備案: DRV8833 モジュール ×2 を MCU の PWM ピンで直接駆動する(PWM 4 本 + 方向 4 本)。
- モーター電源は 5 V(4.8 V 定格に近い)とし、UNO Q の電源とは分けて GND のみ共通にする。

### 5.3 電源

| 系統 | 供給 | 消費の目安 |
| --- | --- | --- |
| UNO Q + LD06 | USB-C 5 V(3 A 出力のモバイルバッテリー、または 2S Li-ion + 5 V 3 A 降圧) | UNO Q 1.5〜2 A(要実測)+ LD06 0.18 A(起動 0.3 A) |
| モーター・サーボ | 2S Li-ion + 5 V 3 A 降圧、または同じモバイルバッテリーの 2 口目 | 4 モーター定格 0.8 A、拘束時最大 2.8 A + サーボ |

保護回路付きのモバイルバッテリー(USB PD 対応、300 g 以下、**給電しながら充電できるパススルー対応品**)を第一候補にします。重量が課題になれば 2S Li-ion + 充電・保護基板に切り替えます。MCU 側で電池電圧を監視し、低電圧でホームポジションへ戻す判断材料にします。

LD06 の電源は MCU が制御する MOSFET スイッチを通します。データシートの寿命は 10,000 時間で、24 時間回し続けると約 14 か月で尽きるため、充電ステーションで待機中はモーターを止めます(第 9 節)。

### 5.4 センサー一覧

| センサー | 用途 | 接続 |
| --- | --- | --- |
| LDROBOT LD06(手持ち) | 自己位置推定、周囲の形状 | MCU の UART(230400) |
| PAA5100JE 床面フローセンサー | 並進オドメトリ | MCU の SPI |
| IMU(BNO055 等、必須) | ヨー角 | I2C |
| ToF VL53L1X ×4(前後左右) | 近接停止、ドッキング時の距離 | Qwiic / I2C(アドレス変更または I2C マルチプレクサ) |
| マイクロスイッチ バンパー ×4 | 接触時の非常停止 | MCU デジタル入力 |
| リフト接触スイッチ | 台との接触、持ち上がり | MCU デジタル入力 |
| 電圧分圧 | 電池監視 | MCU アナログ入力 |
| 前方 ESP32-CAM | 下半身検出、台の脚検出、色識別 | Wi-Fi |
| DFPlayer Mini + 小型スピーカー | 電子音による意思表示(5.5 節) | MCU の UART + BUSY 入力 |
| 圧電ブザー(予備) | 簡易な合図音 | MCU の PWM |
| 外部 ESP32-CAM ×1〜2 | 玄関の人物、扉 | Wi-Fi |

### 5.5 音声出力回路(小姓語の再生)

小姓語の音は PC で合成した WAV を microSD に入れ、DFPlayer Mini(UART 制御の MP3 / WAV 再生モジュール、内蔵アンプ付き)で鳴らします。MCU から曲番号と音量を送るだけで再生でき、Linux 側の音声出力の有無に依存しません。

```text
 UNO Q MCU (3.3 V)                DFPlayer Mini                 スピーカー
 ───────────────                 ─────────────                 ──────────
 TX  ──── 1 kΩ ──────────────→  RX
 RX  ←───────────────────────  TX
 D(入力) ←───────────────────  BUSY   (再生中 = L)
                               VCC ←── 5 V(モーター系と同じ 5 V、100 µF + 0.1 µF で分離)
                               GND ──── 共通 GND
                               SPK+ ─────────────────────────→ 8 Ω 3 W 小型スピーカー(+)
                               SPK- ─────────────────────────→ 同(−)
 D(PWM 出力) ── 100 Ω ── NPN ──→ 圧電ブザー(予備、単純な合図音)
```

| 項目 | 方針 |
| --- | --- |
| モジュール | DFPlayer Mini(秋月で購入可)。電源 3.2〜5 V、UART 9600 bps、内蔵アンプでスピーカー直結 |
| 接続 | MCU の UART(D0/D1 とは別のピン、Software Serial でも可)。DFPlayer の RX には 1 kΩ を直列に入れる(5 V 系との混在時の保護。3.3 V 駆動でも入れておく) |
| 電源 | 5 V。再生時に 100 mA 前後のピークが出るので、DFPlayer の VCC 直近に 100 µF と 0.1 µF を置き、UNO Q の 5 V ではなくモーター系の 5 V から取る |
| スピーカー | 8 Ω 3 W、口径 28〜40 mm。LEGO フレームの前面に小さな穴を開けて前向きに固定。振動が IMU に伝わらないようゴムワッシャーで浮かせる |
| BUSY 信号 | 再生中 L。MCU はこれで「音は一度に 1 つ」を守り、1.5 秒以内の連続要求をまとめる |
| 音量 | DFPlayer のコマンドで 0〜30。日中 20、夜(22 時以降)10、独り言はさらに −6 dB 相当(3 段階下げる)。深夜は「どいて」「あっ」以外を鳴らさない |
| ファイル | microSD(FAT32)の `mp3/0001.mp3` 形式か、`01/001.wav` のフォルダ形式。番号と小姓語の文の対応表をリポジトリに置く(`sounds/index.csv`)。WAV はデコーダーアプリの書き出しをそのまま使う |
| 予備 | 圧電ブザーを MCU の PWM で鳴らす簡易版。DFPlayer が届く前や、SD 読み込み失敗時の合図(「あっ」相当)に使う |
| 代替 | 音質や音量が足りなければ、DFPlayer の DAC 出力(DAC_R / DAC_L)を PAM8403 クラスの小型 D 級アンプに入れて 3 W スピーカーを鳴らす。Linux 側で合成したい場合は I2S DAC アンプ(MAX98357A)を検討するが、UNO Q の I2S ピンの露出は要確認 |
| ノイズ対策 | スピーカー線をカメラや LD06 の配線と束ねない。モーターの逆起電力が乗るので、DFPlayer の GND はモータードライバの GND と一点で落とす |

音の発火は Linux 側の行動状態機械が決め、Bridge で「文番号 + 音量」を MCU に送ります。MCU は BUSY を見て再生し、完了を返します。

## 6. カメラとストリーミング

### 6.1 カメラの配置

| カメラ | 位置 | 視野 | 役割 |
| --- | --- | --- | --- |
| 外部カメラ A | 玄関が見える壁の高い位置 | 玄関と扉 | 人物検出・識別、玄関到着、扉の開閉。ローバーの位置推定には使わない |
| 外部カメラ B(任意) | 廊下の入口側 | 廊下 | 人の接近方向 |
| ローバー前方カメラ | 床上 8〜10 cm | 前方の下半身・足元・台の脚 | 靴の着脱、しゃがみ、荷物、ドッキング、台の色 |

### 6.2 ESP32-CAM の運用

- AI-Thinker ESP32-CAM(OV2640)を標準品とし、MJPEG を HTTP で配信する。フレームレートが不足すれば XIAO ESP32S3 Sense に置き換える。
- 解像度は 640×480 で 10〜15 fps を目標にする。検出は 320×320 に縮小して処理する。
- UNO Q 側は OpenCV の VideoCapture で URL を開き、フレーム取得→処理→結果を共有メモリ(または ZeroMQ)に書く独立プロセスにする。
- 遅延は 100〜300 ms を見込む。位置制御はカメラに頼らず LD06 とフローセンサーで行うので、この遅延は認識だけに影響する。
- 2.4 GHz Wi-Fi の混雑が懸念される場合は、ローバー専用の SSID を用意する。

### 6.3 玄関イベントの検出

外部カメラ A で次を検出します。

- 人物検出(全身が見えるので既存の軽量モデルを使う。UNO Q の Video Object Detection Brick、または YOLO の小型モデル)。
- 人物識別: 家族 3〜4 人の識別を、全身画像の分類モデルで行う(自宅データで学習)。顔認識は使わない。
- 扉の開閉: 扉領域の画像変化 + リードスイッチ(ESP32 側の GPIO で検出し、同じ Wi-Fi で通知)。物理センサーを併用して誤検出を防ぐ。
- 位置の時系列: 人物の足元位置から「玄関へ接近」「玄関で停止」などを判定する。

## 7. 判断と身体制御

### 7.1 LAYA(サーバー側)

| 項目 | 内容 |
| --- | --- |
| 種別 | 非自己回帰の System 1 Decision Model。テキストの「状態」と型付き質問を与え、1 回の順伝播で答える |
| 出力の型 | choice(選択肢から 1 つ)、score(段階)、noul(yes/no の確率)。各答えに確率と確信度が付く |
| チェックポイント | laya(ModernBERT-large、421M)、laya-multilingual(mmBERT-base、322M)、laya-typed-decisions(421M) |
| ライセンス | Apache 2.0 |
| 実行場所 | 自宅 PC(NVIDIA GPU)。GPU なら 1 問 数十 ms。クラウドには出さない |
| Jev との関係 | Jev は TypeSafe AI のクローズドなホスト API。LAYA はその互換のオープン実装 |

LAYA の出力は離散の型付き判断で、**連続値の速度指令は出せません**。LAYA には「何をするか」だけを任せます。

- next_action(choice): WAIT、GET_FATHER_STAND、GET_MOTHER_STAND、GET_CHILD_STAND、BRING_UMBRELLA、RECEIVE_ITEMS、STORE_STAND、RETURN_HOME、OBSERVE_ENTRANCE、OBSERVE_LEFT、OBSERVE_RIGHT
- going_out(noul): 外出するか
- urgency(score 0〜2): 急ぐか

Active Perception は OBSERVE 系の行動を選択肢に含めることで表現します。

状態テキストの例:

```text
time: 07:42 weekday
routine: weekday morning: father out 0.8, daughter out 0.9; weekday evening: father home 0.7, daughter home 0.8
weather: rain, 18C
door: closed (last opened 14 min ago)
person: father (0.83) hallway -> near_shoes -> bending -> standing near door
lower_body: shoes_on 0.91, bag 0.72
father_stand: stored at home slot (red)
mother_stand: stored (blue)
rover: home (x=0.2, y=0.1), battery 78%, last_action WAIT x6
```

### 7.2 通信とフォールバック

- 機体は状態テキストを JSON で送り、3 問の答えを受け取る。送るのはテキストだけで、画像は送らない。
- 応答が 500 ms なければ直前の行動を維持する。
- 5 秒なければ WAIT に落とす。台を持っていれば安全な位置で降ろしてから RETURN_HOME。
- サーバー停止中も MCU の安全停止と Linux 側の自己位置推定は動き続ける。

### 7.3 機体側の学習ベース身体制御(Physical AI)

「どう動くか」の一部を、機体上で動く小さな学習モデルに置き換えます。古典制御は常にフォールバックとして残します。

| 対象 | 入力 | 出力 | 学習方法 |
| --- | --- | --- | --- |
| ドッキング・潜り込み | 台の脚の検出位置、ToF ×4、直前の指令 | vx, vy, ω | 模倣学習。Phase 3 の古典制御と手動操縦のログを教師データにする |
| 人への接近・受け渡し位置 | 下半身検出の結果、ToF | vx, vy, ω と停止判断 | 模倣学習 + 「人が動かずに受け取ったか」の結果で追加学習 |
| 機体側の速い意図予測 | 状態系列 | 30 秒以内に外出する確率 | 記録済みの系列で学習。LAYA の判断を待たずに玄関方向へ寄る「構え」に使う |

規模は数万〜数十万パラメータの MLP または GRU で、UNO Q で数 ms で動きます。

やらないこと:

- 学習ポリシーにリフトの上げ下げを任せない。リフトは古典制御の条件(脚の相対位置と ToF が範囲内)を満たしたときだけ動かす。
- 最初から強化学習で身体制御を学ばない。家庭内で試行回数を稼げないので、模倣学習から始める。

### 7.4 生活パターン(事前知識)

家族の生活パターンを事前知識として持ち、観測が少ない段階でも「外出らしい」「帰宅らしい」を判断する材料にします。最初は本人の知識を手で入力し、運用ログで更新します。

初期値(2026-09-24 に聞き取り。時間帯は要確認):

| 曜日 | 時間帯 | 人 | 傾向 | 初期確率 |
| --- | --- | --- | --- | --- |
| 平日 | 朝(6:30〜8:30 目安) | 娘 | 出かける | 0.9 |
| 平日 | 朝(同上) | 父 | 出かける | 0.8 |
| 平日 | 夕方(16:00〜20:00 目安) | 娘 | 帰ってくる | 0.8 |
| 平日 | 夕方(同上) | 父 | 帰ってくる | 0.7 |
| 平日 | それ以外 | 娘・父 | 特になし | 0.2 |
| 休日 | 終日 | 全員 | 不明(ログで学ぶ) | 0.3 |
| 全日 | 全時間 | 母 | 不明(ログで学ぶ) | 0.3 |

使い方:

- **LAYA への入力**: 状態テキストに `routine:` の行として、その時刻・曜日・人に当てはまる傾向だけを書く(7.1 の例)。
- **ルールベース**: 外出判定に必要な兆候の数を、傾向が強い時間帯は減らす(通常は「靴を履く + 扉へ接近」の 2 つ、平日朝の娘・父は「扉へ接近」だけで候補にする)。帰宅判定は「扉が開く + 夕方の傾向」で、人物識別の確信度が低くても娘・父の台を候補にする。
- **機体側の意図予測**: 学習モデルの入力特徴に曜日・時刻・人物の傾向値を入れる。
- **構え(先回り)**: 平日朝の時間帯は、独り言をやめ、玄関が見える観測位置に早めに移動しておく(OBSERVE_ENTRANCE の優先度を上げる)。台を玄関に運ぶのは、あくまで実際の兆候を見てから。

学習と更新:

- 記録: 人ごとに「扉が開閉した時刻」「外出か帰宅か」を 1 件ずつログに残す(Phase 5)。
- 集計: 人 × 平日/休日 × 30 分刻みで外出・帰宅の頻度を数え、平滑化して確率にする。週 1 回更新する。
- 上書き: 手で入力した値は `routine.yaml` に置き、集計値と手入力値の重み付き平均を使う(最初は手入力 1.0、4 週後に集計 0.7)。学校の休みや出張のような例外は手で一時的に書き換える。

注意: 生活パターンはあくまで事前確率で、観測を置き換えるものではありません。パターンに合わない行動(休日の朝の外出など)も、兆候が揃えば通常どおり判断します。逆に、パターンだけで台を運ぶことはしません。

### 7.5 ルールベースとの比較

同じ状態テキストから同じ行動を決めるルールベース版を用意し、LAYA の判断と一致率・誤介入率を比較します。

## 8. 認識モデル: ローバー視点の下半身検出

ローバーの前方カメラは床上 8〜10 cm にあるため、人の上半身は映りません。この視点の画像を自分たちで収集・ラベリングして検出モデルを学習します。詳細は[データセット計画](../dataset/)にまとめました。要点は次の通りです。

- クラス案: `feet_socks`、`feet_shoes`、`feet_bare`、`shoe_on_floor`、`hand_low`、`bag`、`umbrella`、`stand_leg`、`door_gap`。
- モデル: YOLO 系の最小モデル(YOLOv8n / YOLO11n 相当)を自宅 PC の GPU で学習し、ONNX に変換して UNO Q の CPU で実行。目標 5 fps 以上。
- 代替: Edge Impulse で FOMO / YOLO を学習し、App Lab の Video Object Detection Brick として配備。
- 人物識別はこの視点では行わず、外部カメラの全身画像に任せる。

## 9. 待機・充電ステーション・常時監視

ローバーは常時稼働します。待機位置を充電ステーションにし、待機中も玄関を監視し続けます。

### 9.1 充電ステーション

| 項目 | 方針 |
| --- | --- |
| 場所 | 収納スペースの一角。台の収納スロットと同じ並びに置き、LD06 から見て壁と棚が近い位置にする(位置推定の初期位置としても使う) |
| 給電 | 壁の USB 電源アダプター(5 V 3 A 以上)からステーションの接点へ。ローバー側は底面または後面のばね接点(ポゴピン)で受ける |
| 接点の先 | ローバーのモバイルバッテリーの入力(USB-C)へ配線し、パススルーで機体に給電しながら充電する |
| 誘導 | ステーションに LEGO の V 字ガイドを付け、後退で入ると機械的に中心が合う。最終位置は後方 ToF と接点の通電で確認する |
| 逆接・短絡 | 接点はダイオードで保護し、ステーション側は電流制限付きにする。金属異物が乗っても燃えない構成にする |

台のドッキングと同じ「ウェイポイント → 前方カメラ / ToF → 機械的な芯出し」の手順を使うので、Phase 3 のドッキングと同時に作ります。

### 9.2 待機中の動作

| 項目 | 待機中(ステーション上) | 行動中 |
| --- | --- | --- |
| LD06 | 停止(MOSFET で電源断)。出発の 3 秒前に起動 | 回転 |
| 外部カメラの監視 | 継続。2〜5 fps の人物検出、動きがあれば全速 | 継続 |
| 前方カメラ | 停止または 1 fps | 10〜15 fps |
| LAYA への状態送信 | 継続(0.5〜1 秒周期) | 継続(0.2〜0.5 秒周期) |
| 電力 | ステーションから供給。電池は満充電を維持 | 電池 |

### 9.3 常時監視のための通信

- 外部 ESP32-CAM は壁の USB 電源で常時稼働し、MJPEG を配信する。ESP32 側で簡単な動体検出(フレーム差分)を行い、動きがあるときだけ UNO Q が全速で受ける。
- イベント(扉のリードスイッチ、人物検出、ローバーの状態)は自宅 PC 上の MQTT ブローカーで配る。ESP32 は publish、UNO Q と PC は subscribe。
- ローバーの Wi-Fi は固定 IP にし、切断時は自動再接続する。ストリームが 5 秒止まったら再接続する。
- 監視の処理を UNO Q ではなく PC に置く案もある。PC は LAYA のために常時稼働しているので、外部カメラの人物検出を PC で行い、結果だけを MQTT で流せば UNO Q の負荷と発熱を下げられる。どちらにするかは Phase 5 で UNO Q の連続稼働時の CPU 使用率と温度を見て決める。

### 9.4 常時稼働の懸念

| 懸念 | 対策 |
| --- | --- |
| LD06 の寿命(10,000 時間) | 待機中は停止。1 日の回転時間を 2 時間以内に抑えれば 10 年以上 |
| UNO Q の発熱 | 待機中は認識のフレームレートを落とす。ヒートシンクを付け、温度をログに残す |
| Wi-Fi の混雑 | ローバー専用 SSID、または 5 GHz 帯(ESP32 は 2.4 GHz のみなので、カメラは 2.4 GHz、ローバーと PC は 5 GHz) |
| 深夜の誤作動 | 時刻を状態に含め、深夜帯は WAIT の優先度を上げる規則をルールベース側に持つ |
| 電池の劣化 | 満充電維持の劣化を抑えるため、パススルー品の充電制御に任せる。半年ごとに容量を確認 |

## 10. 表現: 電子音による意思表示

言葉は使わず、R2-D2 のような電子音(ピロピロ、口笛、うなり)で気持ちと状況を伝えます。話しかけなくてよい、という企画の姿勢に合わせ、音は短く、押しつけがましくないものにします。

### 10.1 音の語彙

| 場面 | 伝えたいこと | 音の性格 |
| --- | --- | --- |
| 台を差し出したとき | 持ってきたよ | 上昇する短い 2 音 + 軽いトリル。明るく |
| 帰宅した人を迎えたとき | おかえり | ゆるやかに下がる暖かい口笛 2 回 |
| 扉が閉まり外出を確認したとき | いってらっしゃい | 上昇して伸びる口笛 1 回 |
| 観察位置へ移動するとき | 見に行くね | 短い問いかけ調(語尾上がり)の 1 音 |
| 判断に迷っているとき | どうしよう | 小さく揺れる音を 1 回 |
| 障害物で停止・接触したとき | あっ | 低い短音。繰り返さない |
| 電池が少ないとき | 帰るね | 下がる 2 音 |
| 充電ステーションに着いたとき | ただいま | ごく小さい 1 音 |

### 10.2 実装

| 項目 | 方針 |
| --- | --- |
| 音源 | PC 上の Python で合成(正弦波のスイープにビブラート、短いノイズ、フィルタを重ねる)。WAV / MP3 に書き出して microSD に入れる |
| 再生 | DFPlayer Mini(UART 制御の MP3 モジュール、秋月で購入可)+ 3 W 程度の小型スピーカー。MCU の UART から曲番号を指定して再生 |
| 予備 | MCU の PWM で周波数スイープを直接鳴らす簡易版。DFPlayer が届く前や短い合図に使う |
| 音量 | 時刻で切り替える。日中は普通、夜 22 時以降はごく小さく、深夜は「あっ」以外を鳴らさない |
| 発火元 | Linux 側の行動状態機械の遷移(RECEIVE_ITEMS 完了、扉閉鎖の確認など)で MCU に再生指令を送る。学習ポリシーや LAYA は音を直接鳴らさない |
| 同時発話 | 音は 1 度に 1 つ。1.5 秒以内の連続発火はまとめる |

家族が「どの音が何か」をすぐ覚えられるよう、日常で使う語彙は 8 種類程度に抑え、意味が近い音は似た形にします(帰宅系は下降、外出系は上昇)。そのほかに、人がそばに留まったときの雑談(20 語)と、待機中に誰もいないときの独り言(14 語)、数(1〜3)を持ちます。独り言は息(K)を付けず、遅く小さく鳴らします。音の高さ・形・時間の定義、語彙、文法は[小姓語](../language/)にまとめ、[デコーダー / 合成器](../decoder/)で音と日本語を相互に変換できます。

## 11. 安全設計

- MCU 側で ToF が 12 cm 未満、またはバンパー押下を検出したら、Linux 側の指令に関係なくモーターを停止する。
- Linux 側からの速度指令が 300 ms 途切れたら停止する(ウォッチドッグ)。
- 速度の上限を MCU 側で 0.15 m/s に固定し、Linux 側やサーバーの不具合で暴走しないようにする。
- 自己位置を見失ったら停止する。1 秒以上 LD06 の位置合わせが失敗したらフロー + IMU だけで継続し、5 秒で停止する。
- 柱マスクの角度に地図上の障害物が重なる姿勢では、ToF とバンパーが最後の砦になる。ToF は柱の外側(四隅ではなく前後左右)に置く。
- 充電接点は電流制限とダイオード保護を付け、通電はステーション側で検出したときだけにする。
- 物理的な電源スイッチをモーター電源側に付け、手で止められるようにする。
- リフトを上げたまま速度を出さない(上昇中は 0.08 m/s に制限)。
- 人の足元 30 cm 以内では自動的に減速する。
- 家庭内の映像・人物データはリポジトリに入れない(`.gitignore` で `data/`、`captures/` 等を除外済み)。サーバーへ送るのはテキストの状態だけにする。
